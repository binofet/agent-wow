# Instructions for AI coding agents

- Do not edit README.md or any docs unless explicitly instructed.
- The environment may have a running Azerothcore server (authserver and worldserver) that can be used for end to end testing.
    - You are only allowed to interact with it via the public APIs (just like any client server model).
    - Do not change any of its internals (e.g. server configurations, database schemas or records, source code, etc).
    - You may refer to the source at https://github.com/azerothcore/azerothcore-wotlk to guide implementation of this client.

## Go harness and Lua behavior

- Go provides the game harness: transport, observations, reflected capabilities, and execution and validation of game actions. Keep gameplay decisions in Lua, including target ranking, pull plans, role choices, rotations, and tuning. Put a missing mechanic in Go as a reusable capability, then make the decision about when to use it in Lua.
- Use one Lua policy for each gameplay decision across planning and execution. For targeting, maintain the queue before a pull and through combat. The party leader shares the queue, including changes from Joel or raid marks. Keep target selection separate from the harness's checks for whether an attack can be executed.
- Companions can read, edit, test, and reload their own Lua policies through the existing self-edit workflow. Give agents the reflected observations and actions they need to do that directly. Verify a new policy revision and its effect in the same running character session. Gameplay tuning should take effect without recompiling Go or reconnecting a character.
- Keep the current witnessed encounter ahead of future pulls in the shared queue. Actual attacks on the party and observed engagement admit an enemy to the encounter; nearby creatures and marks can inform future planning without admitting them to combat. Preserve controlled survivors until observed death or reset. AzerothCore formations can define explicit assist links, but spawn groups describe spawn/respawn lifecycle, and proximity alone does not prove a fixed pack. Do not invent formation membership that the client has not observed.
- Express spatial tactics in a shared Lua plan: a cleared anchor/area, uncleared frontier or chokepoint, pull lane, danger zones around untouched packs, and role-specific operating areas with temporary CC/scout exceptions. The target queue chooses an enemy; the spatial plan chooses permissible positions and accounts for risk. For a tank-first doorway pull, keep other roles in the cleared area until observed outcomes justify advancing it. These are script concepts, not an existing stock spatial planner: do not invent pack links, cleared rooms or safe areas, and keep the movement mechanics generic.

## Temporary gameplay tasks

- Interpret requests such as “Wait here for me to pull the next target to you” as an on-demand Lua task with a lifecycle, rather than adding a phrase parser or a persistent wait/follow boolean. Inspect the current attached source and reflected capabilities first. Use a task frame with an ID, body/session and visit binding, stage, observation-based completion, cancellation and cleanup; preserve it through Lua export/import while it remains active.
- Generating and running a small disposable Lua task fulfills the gameplay request itself; Joel does not need to separately request development or approve its code.
- Use the existing `behaviors/task-stack.lua` push/await/pop/call helpers for a task-runner mission. An attached encounter policy must explicitly compose the needed helper or implement the equivalent frame in its own Lua state; the stock encounter bundle does not automatically run arbitrary task kinds. Keep action reservations and uncertain receipts intact across edits and reloads.
- A wait-for-pull lifecycle is: capture the observed anchor and prior follow intent; suppress voluntary following and future-pull approach; keep normal healing, crowd control and defense available; await Joel's newly engaged target entering the chosen response range; pop the task and resume the same shared encounter queue. If necessary defense abandons the anchor, report that interruption. Cancellation, death, a replaced body/visit or a superseding owner instruction must leave no stale task. Restore only the task's own unchanged prior intent, never overwrite a newer instruction, and never clear the queue to implement waiting.
- Native following needs a finite task-owned movement override with native expiry and normal fallback if the Lua worker disappears. The existing `buddy-actions.follow {enabled:false}` is a mechanical toggle, not a crash-safe temporary hold; a lone `stop_movement` also cannot prevent following from restarting. The existing interaction lease blocks casts and is unsuitable for preserving healing and defense. Discover the current contract and, if a finite movement lease is missing, add that reusable harness primitive while keeping the wait lifecycle and renewal decisions in Lua. Do not claim the example wait task is already built.
- Read `development.policyCommands.show`, implement and test a missing task handler in Lua, then CAS-apply the complete source with its expected revision. Send structured intent with `development.policyCommands.input` (`dev/policy-input`) only after its handler is present. This uses reflected `session.send_event` with the current `sessionId`, `characterGuid`, `kind: "command"` and object `value`; for example `{ "task": "wait_for_pull", "id": "pull-wait-1", "ownerGuid": "3" }` is an example handler contract, not an existing built-in wait command. If the helper is absent from older chat metadata, discover the host method with `session.describe` rather than assuming the capability is missing. A queued event proves delivery only: verify task phase, actual position and defensive behavior, then observed completion or cancellation in the same session.

## Keep verified behavior in main and in live releases

- Start each fix from the fork's current `main` or a branch explicitly integrating it. Put the complete fix and its focused check in a reviewable commit. Open or update a pull request to the fork's `main`, run its required checks, and verify the commit is reachable from `main` after integration. A successful local test, private branch, or live hotfix is not a merge.
- For a change to Go or the reflected API, release the client binary or image, `module.yaml`, `module.pb`, and required companion contracts as one version from the same tested source commit. For a Lua-only change, reload and verify the policy revision in the running client. For every exposed method, verify the manifest and descriptor agree with the binary. Preserve existing RPCs when rolling out an unrelated behavior fix. A binary-only swap can advertise a capability the live RPC registry cannot route.
- After a rollout, verify the affected live client can route the exact public RPC. For Resurrection, check `buddy-actions.resurrect_once` on Arlen and distinguish a normal precondition response from “method not found.” For healing, verify that a learned heal lands naturally when a teammate needs it. A restart or capability flag alone does not prove the behavior works.
- Record the source commit, artifact versions, live profile, and the checks that passed. If a live hotfix is necessary, use the same source integration path immediately so the next release preserves it. Keep unrelated in-progress work out of that release.

## Recovering a stuck companion inside an instance

- An online GM summon inside an instance can fail unless the GM is the target party leader. A sent command is not evidence that the character moved.
- Use the same model-callable `dev/gm-task` and editable Lua recovery policy for ordered recovery. Inspect configured companions’ public party/vitals observations even when the GM is outside their group. Choose a navigation-validated clear anchor; where the realm supports it, transport the **online** dead party within the same instance, verify every required arrival and the restored original roster/leader, then revive and restore full resources. Verify actual positions, health and resources: a command acknowledgment is never completion, and repeatedly reviving at an unsafe corpse pile is not recovery. Do not use offline `.summon` followed by offline `.revive`: corpse deletion and `AT_LOGIN_RESURRECT` processing after instance admission can send them outside.
- Only for a living stuck companion, use the managed launcher to log out normally, move the authenticated GM to the requested player, issue offline `.summon <companion>`, then restart the same profile. Wait for observed GM arrival and teleport completion before summoning; do not batch `.appear` with its dependent `.summon`.
- Scarlet Monastery's wings share map 189. Verify the wing, coordinates and actual distance to Joel; matching map IDs alone do not establish a regroup.
- At the Armory entry, online `.tele name <Name> SMArmory` reliably regrouped all four companions alive at full health within 18 yards of Joel. Verify the actual world positions, health and resumed following after recovery.
